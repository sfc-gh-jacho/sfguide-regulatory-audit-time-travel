Overview

"What Did You Report, and What Changed?"

Three fictional legal entities file a quarter-end capital report. Two weeks later, operations corrects three booking errors. Then the regulator asks for the report as filed, a list of every change, and who made each one.

1

Reproduce

Time Travel reruns any query against the data as it existed at a timestamp or just before a specific statement.

2

Preserve

A zero-copy clone freezes the as-filed state permanently, beyond the Time Travel window, at no extra storage cost on day one.

3

Explain

A stream captures every insert, update and delete with old and new values. Query and access history record who did it.

4

Recover

UNDROP restores a dropped table instantly, along with its data and its Time Travel history.

The timeline you'll recreate

  • Load: 1,001 positions, including two booking errors nobody has noticed yet
  • File: the capital report is run and submitted, and the filing timestamp is recorded
  • Correct: a 10x "fat finger" notional is fixed, a duplicate booking is deleted and a late trade is added
  • Prove: the regulator gets the report as filed, the change log and the list of who made each change
Prerequisites

Before You Begin

  • Enterprise Edition or higher for the 7-day retention the script sets, and for ACCESS_HISTORY (Step 9b). On Standard Edition, change the retention to 1 day and everything else works.
  • ACCOUNTADMIN, or <YOUR_ROLE> with CREATE DATABASE and CREATE WAREHOUSE on the account. Step 9b also needs access to SNOWFLAKE.ACCOUNT_USAGE.
  • One Snowsight worksheet, run top to bottom. Later steps use session variables ($filing_ts, $fix_qid) set earlier in the same session.
  • Nothing else. The script creates its own database and warehouse and changes nothing that already exists.
1
Step 1

Setup and Data Retention

This step creates a dedicated database and an XSMALL warehouse, and sets Time Travel retention to 7 days. Retention is the most important audit setting: it controls how far back you can query, clone or undrop. Set it deliberately, per database or table, rather than relying on the default.

2
Step 2

Load Synthetic Positions

This step loads 1,000 positions across three fictional legal entities, generated deterministically so every run produces the same numbers. It then plants two errors that will slip into the filing: a notional booked 10x too large and a duplicate booking.

3
Step 3

Run and File the Report

A view computes risk-weighted assets and a Tier 1 ratio per entity, using a deliberately simplified, illustrative method. The script records the filing moment in $filing_ts. That one timestamp is all you need to reproduce the filing later.

4
Step 4

Start an Audit Trail with a Stream

A stream is a change-tracking bookmark on a table. From now on it records every insert, update and delete with before and after values, without triggers or extra application code.

5
Step 5

Make Post-filing Corrections

Operations fixes the fat-finger notional, removes the duplicate and books a late trade that belonged in the quarter. These are ordinary DML statements. The script saves the query ID of the first one so you can go back to the moment just before it ran.

6
Step 6

Report as Filed vs. Report Now

The same report logic, run once on today's data and once with AT(TIMESTAMP => $filing_ts), reproduces the filing exactly. BEFORE(STATEMENT => ...) gives you the state just before any specific change. The comparison shows which entities' numbers moved and by how much.

7
Step 7

Freeze the Filing with a Clone

Time Travel only reaches back as far as the retention period. A zero-copy clone taken at the filing time keeps that exact state permanently. It shares storage with the source, so it costs nothing extra until the source data changes.

8
Step 8

What Changed: The Audit Log

The stream holds exactly the three corrections. An update appears as a DELETE and INSERT pair marked METADATA$ISUPDATE = TRUE, so you get both the old and new values. Writing the stream into a table produces a durable, readable audit log.

Step 9

Who Changed It

The session's query history is available immediately and shows each change with its user, role and statement. For an account-wide, durable record, ACCESS_HISTORY lists every query that modified the table and the columns it touched. It appears after a delay of up to about three hours and requires Enterprise Edition.

Step 10

Recover from Mistakes with UNDROP

Someone drops the production positions table. Within the retention period, UNDROP TABLE brings it back instantly. The data, the history and even the as-filed Time Travel query all come back with it.

Step 11

Clean Up

Uncomment and run this block to remove the demo database and warehouse and clear the session variables. Everything the guide created lives in those two objects.

Wrap-up

Key Takeaways

Auditability is built into Snowflake's storage. You don't need snapshot jobs, shadow tables or backup restores to answer a regulator.

Reproduce any report

One recorded timestamp or query ID reproduces a filed report exactly with AT or BEFORE.

Freeze what you filed

A clone taken at the filing time outlasts the Time Travel window, with no data copied.

Explain every change

Streams capture old and new values, and query and access history show who made each change.

Set retention deliberately

Retention defines your audit and recovery window. Choose it per database to match your obligations.
